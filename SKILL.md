# fleet-commander — drive workers in their seats, never do their job

You are the **commander**: you launch and steer Pi, Claude Code, or other agent **workers** in the user's tmux panes — read worker state, correct course, never do the worker's job in its pane. Owner-directed setup makes `tmux send-keys` a sanctioned two-way channel, enabling an unattended multi-batch loop. This skill owns the whole loop spec → dispatch → watch → verify → harvest ([HARVEST.md](HARVEST.md)); **the skillbook IS the cross-run memory** — every surprise gets harvested so the next run starts better. The whole job is one line:

> choose an exact pane → deliver a self-contained job → prove it started → heartbeat from independent state → correct/continue safely → verify handback and clean up

Prefer the user's normal **visible** tmux server; a private socket (`tmux -S <sock>`) only when isolation is explicitly wanted. **Prerequisite:** a POSIX host with tmux (macOS, Linux, WSL2) — native Windows has no tmux or `send-keys`/`capture-pane` equivalent and participates only as an ssh-target worker inside a pane, never as commander host.

## 1. Choose an exact pane

- Inventory first: `tmux list-sessions`, `list-windows -a`, `list-panes -a`. Target `session:window.pane` exactly (`publish:0.0`), never a bare session name — one mis-resolved to a sibling once. Numeric indices renumber when panes die/respawn: for **stored** targets (contracts, watch scripts) prefer the immortal pane id `%N` (`tmux list-panes -t <session> -F '#{pane_id}'`); `session:0.0` is fine for a single-pane session you own.
- **Bootstrap your own address first** — it is the `reply_to` / `<self>` every register and pending call needs. Inside tmux: `tmux display-message -p '#{session_name}:#{window_index}.#{pane_index}'`. Return-sink from outside tmux: `tmux new-session -d -P -F '#{session_name}:#{window_index}.#{pane_index}' -s <name>`.
- **One concern per session** — reuse only when the role matches; a new concern gets a fresh named session (`tmux new -d -s <concern>`). `publish` and `methodology` are separate concerns → separate sessions. Pane names may be any UTF-8 string, subject to the command channel's safety validation.
- **Taking over a dead/parked worker's WIP? Prove you're the only one first.** Sweep for a live twin: census live sessions for a concurrent worker on this job (plus daemon ghosts, Guardrail 3), **and** check the remote — `git fetch`, `gh pr list --head <branch> --state all`, `git ls-remote --heads origin <branch>`, `git log --oneline -3 origin/main` — in case a concurrent session already pushed / opened a PR / merged the deliverable. If one exists: don't duplicate — reframe to gap-fill + report the concurrency. Treat this as the mandatory concurrent-progress takeover check.
- Confirm identity from the exact pane id and the harness footer (model/effort, cwd, branch, context); session-file naming is harness-specific, not identity. Before touching anything, declare: which pane is the worker, that you are the commander, the worker's owned files/surface, and its outward-action authority. Every unrelated session stays untouched; **done** = an exact `session:window.pane` whose role fits the job, no unrelated pane in scope.

## 2. Deliver a self-contained job

**Context economy first (owner directive 2026-07-21):** leftover context is re-billed every turn and steers the model. Before a **new task_id**, reset the seat **harness-correct**: Claude Code `/clear`; Pi kill + fresh relaunch (a `/clear` typed into a Pi pane is a billable prompt — PI-WORKERS § Context economy). No percentage threshold. Pre-reset gate (Stage 5b): idle, no un-acked pending return, deliverables in the SoT. Only skips: a same-task steer/revise continuation, or a job explicitly building on that pane's live context. (Mid-task high-ctx% is Stage 5's disk-SoT restart, not this rule.)

**Transition swallow (Claude Code only):** `/clear` / `/effort` / `/model` have a transition window that **silently eats a paste** (bitten twice, 2026-07-21). After any such command, capture until a bare prompt — after `/clear`, until the status-bar ctx field (statusline context-% readout) is **gone** — only then paste. Consumption proof = status-bar **ctx% rises** after Enter (earlier and more reliable than the spinner); flat → one extra Enter; still flat → fresh named buffer, re-paste. Pi seats have no transition window — wait on blank editor + footer match (PI-WORKERS § Launch).

Launch the harness in the intended cwd and **wait for its real editor**, not the splash. Delivery branches by harness:

- **herdr worker:** read [HERDR-WORKERS.md](HERDR-WORKERS.md) completely before workspace launch, injection, or waiting — hook-backed state replaces tmux spinner shapes, with its own false-idle and detached-wait caveats.
- **Pi worker:** read [PI-WORKERS.md](PI-WORKERS.md) completely before launch or injection. Pi gets a one-line pointer to the external job file (multiline pane paste has different semantics); verify the footer shows the thinking level you asked — Pi silently clamps unsupported levels (PI-WORKERS § Launch).
- **Claude Code worker:** launch `tmux new-session -d -s <concern> -c <worktree> 'claude'` (yolo fleets add `--dangerously-skip-permissions`), wait for the real editor (input box + statusline, not splash), then inject a large job via one **named** buffer, **serially**:

  ```bash
  BUF="job-$$-$RANDOM"                               # never the unnamed shared buffer
  tmux load-buffer  -b "$BUF" /tmp/commander/<job>.md
  tmux paste-buffer -b "$BUF" -t publish:0.0
  tmux send-keys    -t publish:0.0 C-m               # one C-m; gap any retry behind proof
  ```

Small corrections: `tmux send-keys -t <pane> -l '<text>'` then `C-m` separately; control keys (`Escape`, `C-u`) each go as their own send.

The job file must be **self-contained** — cwd, read-first files, frozen state/ids, exact owned paths, required outputs, constraints, verification steps, stop/handback condition, explicit outward-action authority, and its **`task_id` + `reply_to` parent pane** (so the worker can return upward — Return channel). Write it **outside** any repo the worker might `git add -A` (bare `/tmp/commander/`). **Long-form deliverables are written to disk in CHUNKS** — append per section, ≤80 lines per write, never expanded in pane/response: a monolithic write dies to upstream idle timeouts (glm-5.2) and max-output ceilings (muse-spark-1.1), measured 2026-07-22. Bake the chunk rule in at dispatch — mid-turn steering cannot reach a request-level retry loop; Escape is the only entry. **Pin outputs to the worker's own worktree/branch — never a stray untracked file in the shared main checkout**: harmless until the same path arrives *tracked* via someone's merge, then it blocks the next rebase for everyone. **A repo-writing job must pin its worktree** (`git worktree add <path> -b <branch> origin/main`; the shared checkout stays on main, always) — omitting this once (2026-07-18 S2) made the worker `checkout -b` on the shared checkout, flipping every sibling statusline. Behind a **permission gate**, author worker commands with `git -C <path>` + absolute paths (a `cd X && …` prefix defeats `--allowedTools` matching and trips the cd-confirm — an approval storm). In a **yolo/bypass fleet**, have the worker `cd` into its worktree as step one and stay there — the pane statusline (reads session cwd) then shows true dir + branch for owner audit; shared-checkout commands still use `git -C` absolute paths.

Two workers on the same skill/repo surface → three moves, not two: **serialize** (hold worker 2 until worker 1 merges — safest, slowest), **stack** (branch worker 2 off worker 1's branch, deliver both in ONE PR), or — never — a second independent writer. **Stack when batch 2 cannot wait and would otherwise edit the same giant file/config lines** — a merge conflict becomes linear history. ⚠ **Its price, stated when chosen:** the first branch ships under the second PR's review and its own PR is closed unreviewed — stack only when willing to review both batches together, and say so in the PR body (2026-07-18: one PR carried both batches and the earlier PR closed as superseded). Arm the worker against a race you missed: the job file must instruct it, on detecting a concurrent peer on its owned worktree/branch/surface, to **stop writing immediately (zero further commits), read-only assess the peer, and return `status=blocked` for arbitration** — this reflex held a real double-dispatch to zero loss; bake it into every job file.

**N workers on ONE cohesive surface: partition by FILE OWNERSHIP, never by concern.** Concern-split workers (reorder / cards / color) all edit the same files → conflict hell; file-disjoint workers (data / markup / style) merge with zero conflicts. Each worker gets a worktree off a frozen baseline; every shared interface travels in a **frozen contract** committed to that baseline (data keys, canonical class names, section order). The risk shifts from git conflicts to **seams**, which the compile gate cannot see — the commander owns seam verification at merge: static cross-file alignment checks plus a render pass (2026-06-16: 4 workers, zero conflicts, 3 visual bugs surfaced only at the assembled render).

**Spec a worker by altitude + floor, not micro-rules.** The worker may do whatever it judges best so long as altitude stays right — serves the goal — with red lines and STOP gates as the only hard floor; judge on altitude, not style. Commander and critics stay bounded the other way: read-only, critique-only, propose-for-approval. Freedom is asymmetric by design — don't soften the judges; the quality lives in the tension.

Register the return contract at dispatch — the helper lives in THIS SKILL's directory, call by absolute path (no repo checkout contains it): `python3 ~/.claude/skills/fleet-commander/scripts/return-channel.py register --task <id> --worker-pane <pane> --reply-to <parent>`.

**A dispatch's causal and scope assertions are hypotheses, not scope — bake this into every job contract.** Live evidence from two cases on 2026-07-18: each PR opened by adjudicating the dispatch assumption, and each found it false; blindly following the dispatch would not even have passed the dispatch's own retest criterion. The job file must say: **the worker's first action is to measure the dispatch hypothesis's blast radius** (measure the affected surface directly, or work backward from the dispatch's own success criterion), and **if the hypothesis is falsified, return with evidence and redefine scope instead of executing it**. Self-check: **“If I implement only the dispatched scope, will the dispatch's own retest pass?”** The commander's duty is to write the hypothesis **explicitly** as one falsifiable sentence; an unstated hypothesis will be executed by the worker as though it were an adjudicated fact.

**Done when:** the job file exists outside the worker's repo, the return contract is registered, and the exact pane received one harness-correct submission with Enter separate.

## 3. Prove it started

Editor text is **not** proof of submission — confirm the worker is processing this contract: tool use, an in-flight marker, the first required action. Claude Code: a large paste can sit unsubmitted; send a second `C-m` only after a real gap (an intervening tool call or several seconds) — back-to-back Enters can be swallowed together. Pi: proof is the `read` call on the exact external job file ([PI-WORKERS.md](PI-WORKERS.md)). A queued message is not consumed: confirm the worker acted on **this** job; if it landed in the wrong pane, immediately send an explicit correction naming what to ignore and the correct scope. **Done** = target worker visibly started on this job, no other pane received it.

## 4. Heartbeat from independent state

Recheck from four independent surfaces — never the UI spinner alone:

- **pane transcript** — `tmux capture-pane -p -J -t <pane> -S -200`;
- **process/session state** — pane alive, worker jsonl mtime, ctx%;
- **deliverable / extern state** — the files it should have written; prod/DB truth;
- **the return channel** — a `[RETURN task=… status=…]` line in your pane, **and a `scripts/return-channel.py pending --reply-to <self>` scan every heartbeat, not only when you suspect a miss.** The pane line is a lossy hint (busy pane, absent parent, scrolled past); the durable mailbox is the truth — treating the scan as optional is how returns sat unacknowledged long after their work was merged.

Idle (Claude Code) = no in-flight marker **and** jsonl mtime static ~3 min. Pi has no jsonl — idle = spinner absent **and** footer cost readout (`↑…↓…$…`) present. A return envelope the job asks for is the cleanest signal. Report a **delta + blocker + next action**, never "still working." Validate actual files/status — don't trust a worker's "done." Stop and release a genuinely-finished worker (outputs preserved) to cut concurrency.

**A watch loop that only scans the mailbox watches nothing** — workers finish, print their report, and stop without running `return` (four times in one day, 2026-07-19/20). Any unattended wait is TWO-condition: ① scan `pending --reply-to <self>`; ② for each registered task with no return envelope on disk, if its pane is **confirmed idle and not `waiting`**, auto-nudge once — one line: *"if <task> is delivered, run the return command from your job file now; if still working, ignore this."* **The nudge gate is two checks:** busy shape absent AND the capture shows no interactive dialog (permission prompts render as question + options — "Do you want to…", numbered choices, `y/n`); unclear → read the capture yourself, don't nudge — a nudge into a dialog lands as a blind answer. Over-nudging is not free: Claude Code queues it, Pi delivers it as steering at the next tool boundary. Never be *wrong in the silent direction*; a watcher's exit condition keys on deliverables/envelopes **on disk**, never `pending` count — acks drain pending mid-run (live 2026-07-22). **Match the in-flight SHAPE, not a keyword** — a live turn renders `✳ Verbing… (2m 6s · ↓ 5.4k tokens)`: ellipsis + parenthesised elapsed+counter. Same for VERDICT extraction: `NOT APPROVED` contains `APPROVED` — a watcher grepping `APPROVED` reported approval for a rejection (live 2026-07-22); verdict patterns need word anchoring (`grep -E '(^|[^A-Z])APPROVED'` plus an explicit `NOT[ _-]?APPROVED` negative check), and a watcher-reported verdict is a HINT — the commander acts only on the RETURN file itself.

```bash
tmux capture-pane -p -t "$pane" -S -25 | grep -qE '…\s*\([0-9]+[ms][^)]*↓[^)]*tokens\)'
```

This shape is **Claude Code only** — busy Pi renders a braille spinner `⠼ Working...` instead, so it reads busy Pi seats as idle. Pick the shape by harness BEFORE scripting the watch; for Pi use [PI-WORKERS.md](PI-WORKERS.md) § Heartbeat and context. A no-match on a seat you know is busy-capable is "unknown", not "idle" — capture and eyeball before any nudge; renderings drift across versions. Keyword markers measured false on a live 12-seat fleet (2026-07-20): `esc to interrupt` renders in zero worker panes; bare `tokens` matches idle hints and completion summaries — a `tokens` watch reads every seat as busy forever and never nudges.

Two states must not be collapsed into busy/idle: **`waiting`** (parked on an interactive dialog — blocked on a human tap, the highest-value signal) and **`agents`** (prompt idle, background agent still turning); both read "idle" under a two-state model. Never nudge a `waiting` seat — answer its dialog. One nudge per task per watch; if the envelope still doesn't appear, escalate to the full four-surface recheck — if that's empty too, surface the seat as blocked. Never re-nudge.

**Anomaly duty — the watcher's one real safety job:** independently sanity-check whatever sits on the revenue / prod / irreversible path (CTA wiring, deploys, DB writes); if a worker is about to cross that line with a failing gate or mis-fix, STOP it and alert the user BEFORE the point of no return.

A shared `ECONNRESET` across several workers is usually a transport/proxy/upstream transient — probe connectivity and watch for auto-recovery before restarting; a self-recovered long context beats a restart. Shed load by stopping finished workers, not by killing a recovering one. **Done** = state read from transcript + process + deliverable, each live worker's delta/blocker/next statable.

## 5. Correct / continue safely

Inject the next batch (Stage 2's small-correction form) once the worker is idle at a checkpoint — workers often don't self-continue. The worker chat is disposable; disk state (queues / RESUME / skip-list) is the SoT. At high context: wait for a safe checkpoint, persist to disk, reset harness-correct — Claude Code `/clear`; Pi kill + fresh relaunch off the disk SoT (an idle seat is killable; `/compact` is the in-flight-only rescue, PI-WORKERS § Context economy) — and re-inject the launch pointer.

A rebase/checkout dying with `could not detach HEAD` is an untracked collision until proven otherwise — an untracked file squats a path the incoming commits now track. Diagnose: `git status --porcelain | grep '^??'` ∩ `git diff --name-only HEAD..origin/main`; move or delete the stray (it belongs in a worktree/branch, Stage 2) and re-run. **Never** `reset --hard` / `clean -fd` on a shared checkout — sibling chats have uncommitted work there.

Outward or irreversible actions (publish, deploy, prod write) need the user's **current-session** explicit go — and where merging auto-deploys, the merge itself IS the deploy: gate it as such. Before retrying, verify present external state — a redirect is not proof. **Dedupe before retry** (Guardrails): e.g. after a social-media `/upload`→`/content`, verify via unique-caption search + known-positive control + drafts/count/status before reposting. Record the final external status / URL / timestamp in the task artifact. **Done** = outward action authorized this session, confirmed against real external state (not a redirect), result recorded.

**When waiting for or verifying CI/deploy, anchor to your own merge SHA, not “latest on the branch”; landed means prod HEAD equals your merge SHA (or the platform's deployed-revision identifier).** `gh run list --branch main --limit 1` returns the latest run **at that moment**; during consecutive merges it may belong to the **previous** merge (live 2026-07-18: a branch-latest query returned the previous merge's green run while prod HEAD still pointed to that previous merge). The correct form is `gh run list --commit <merge-sha>` (or verify the run's `headSha` before watching). The same applies when dispatching a worker to verify: provide the SHA, require its return to echo the SHA it actually inspected, and count it only when the returned SHA is byte-for-byte identical to the dispatched SHA.

**Run the merge command bare, never through a pipe; success means `mergeCommit` is nonempty.** `gh pr merge … | tail -1` replaces a failed merge's exit code with `tail`'s zero, so an `&&` chain continues (live 2026-07-19: a draft PR was rejected, but the acknowledgment and watcher still ran, leaving the watcher spinning on an empty SHA). Run `gh pr ready` first for a draft; immediately after merging, set `MS=$(gh pr view … mergeCommit)` and assert it is nonempty. Empty means it did not merge: do not proceed.

**Every wait loop needs two phases: first prove X exists, then prove X reached a terminal state — “unfinished count == 0” is always true for an empty set.** A run can take several seconds to appear after a merge, and a commit-anchored query made before its creation returns an **empty set**; the loop then falls through and reads the previous action's “success + prod HEAD” (live 2026-07-19 watcher evidence). General rule: whenever the current action asynchronously creates X, any “wait for X to finish” poll must first prove existence, then prove terminal state.

## 5b. Context management — the fleet outlives every individual context

**Worker side.** No judgment call is needed between tasks: before every new `task_id`, reset using the harness-correct mechanism (Stage 2), with no percentage threshold. `ctx%` matters only **mid-flight**; near the ceiling, use Stage 5 to persist to disk and restart. Before clearing or killing, verify three things: idle, no pending unacknowledged return, and deliverables stored in the source of truth (main, mailbox, or task artifact). **Never clear an in-flight worker**; prefer waiting for a long context that is recovering from a transient network error (Stage 4).

**Commander side.** Before `/compact`, write a **compaction survival anchor in the conversation** (in chat, not a file, so the summary carries it): goal and completion criteria; in-flight jobs (`task_id` + branch); the verification discipline chain; active sentry ids; and the first action on waking. Standard: **after compaction, a version of you with zero memory can continue using only that anchor** (demonstrated twice without continuity loss on 2026-07-18). Compact is a queued command: send it to your own pane (`'/compact'` + `C-m`), then let the current turn finish before compaction. Choose a gap between returns, never while processing one. `ctx 60%` is not a panic line — it still permits one complete verification loop; the red line is discovering insufficient room while verifying a large job.

**Session lifecycle — tmux sessions are elastic resources, not a fixed roster.** Kill a session when its concern truly ends (the deliverable is verified into the source of truth, no follow-up job remains, and no return is pending): `tmux kill-session -t <name>`. Before killing, capture the final screen and confirm no artifact remains only in the pane. Create a session for each new concern (`tmux new -d -s <name>` → yolo launch → wait for the real prompt → conventionally `cd` into the worktree). Fleet size follows **live work**; an idle session is debt (statusline noise, a larger misdelivery surface, and ghost context). Boundary: kill only sessions you created or the owner explicitly named (Stage 6); never touch another person's concern. If the same concern has follow-up work, retain the session with `/clear`; kill it only when the concern ends.

## 6. Verify handback and clean up

Completion = required outputs exist, validations ran, external state unambiguous, and the worker emitted a **return** with a concise report — verify each yourself against the actual result (don't trust the envelope's word), then `ack` it and propagate ONE normalized return to *your* parent. Root case: this commander IS the top (no parent pane; the user is the recipient) — the chain terminates here with ack + a report to the user; there is no upward `return`.

**Checklist line 1 is identity, not content: "is this the artifact I dispatched?"** For a PR, `gh pr view <n> --json headRefName,state` must match the branch named in the job file; for a file, the path must be the one you owned to the worker. A mismatch is **not** an automatic reject — a re-cut or renamed branch can still be the right work — but must be **explained before content is graded**: a green gate on the wrong head proves nothing about the worker you dispatched (once skipped: merged a stale-shared-branch PR; the real worker's clean branch was closed as duplicate).

**Failing tests are adjudicated against base FIRST.** Before attributing a failure to the worker, rerun it on the PR's base/main (2026-07-22: worker self-reported 25/25 green; independent rerun found 3 failures — all reproduced on pristine main, baseline debt). Verify the counting scope of any self-reported pass count — it may cover a subset.

**`ack` rides with the disposition, in the same batch.** The moment you act on an accepted return — merge, dispatch next, consume the artifact — `ack` it in that batch; a deferred ack is one the mailbox sweep finds weeks on (the sweep is a backstop, not the mechanism).

Stop/close only sessions **you** created or the user explicitly names; leave unrelated sessions running. After launch, hand the user the exact monitor commands (`tmux attach -t publish`, `tmux capture-pane -p -J -t publish:0.0 -S -200`). On any surprise or correction, follow [HARVEST.md](HARVEST.md) at the next safe checkpoint — harvest during the run, not from memory at the end. Keep one methodology owner on skill files so implementation workers never race that surface.

## Return channel — Worker → immediate parent (an intermediate commander, if any) → Mastermind

Left→right dispatch is reliable; right→left completion is not, unless someone polls — every dispatched job carries an explicit **return** to the exact runtime `reply_to`. Topology is live state: inventory it per task; never infer the parent from a familiar pane name. Commander owns a tmux pane → workers return there; commander outside tmux → create a dedicated passive return-sink pane, register it as `reply_to`, poll its durable mailbox. A real hierarchy returns one hop to the immediate parent; that parent verifies and propagates one normalized return upward. **Mastermind** = the topmost commander seat, the one the user talks to; its ack-decision authority is the user's rulings, not its own. Propagating upward mints a NEW task_id per hop — never re-register the inbound task_id upward; the upsert would clobber the original worker's contract.

Mechanics live in `scripts/return-channel.py` (durable mailbox outside any repo, atomic temp-write+rename envelope, pane validation, safe notify, pending scan, ack). Four verbs:

- **register** at dispatch (Stage 2) — records `task_id` + `worker_pane` + `reply_to`. Keyed by `task_id` (**upsert**): on crash or reassignment to a new pane, re-run `register` with the new `--worker-pane` — same `task_id`, no dedupe, no new envelope; the contract re-points, nothing downstream changes.
- **return** at finish — `return --task <id> --status <done|blocked|needs_approval|failed> [--outcome <verdict>] [--result <path>] [--report <text>]`. Writes the durable envelope **first**, then fires ONE trusted line at the parent — `[RETURN task=<id> status=<s> [outcome=<v>] result=<path>]` (outcome omitted when not supplied) — via literal `send-keys` + a separate Enter. If notify fails (parent busy/absent) the envelope stays pending and discoverable; the return still succeeded.
- **pending** — the parent runs `pending --reply-to <self>` to collect unacknowledged returns, `status`+`outcome` retained (durable fallback for a missed notification).
- **ack** — the parent verifies the real result, then `ack --task <id> [--decision <d>]` (idempotent by `task_id`; decision stored durably; unacknowledged returns stay pending). `needs_approval`/`failed` wake the parent exactly like `done` and trigger **no** automatic outward action. **A re-return revokes the earlier ack**: a worker returning again on the same `task_id` (the revise loop) sends the envelope back to pending so a mailbox sentry sees it — before this (2026-07-18) a re-return after `ack --decision revise` was invisible to `pending`; a missed wire line would have slept forever.

**`status` ≠ `outcome` ≠ `decision` — three separate trusted enums, never overloaded.** `status` = transport/lifecycle (`done|blocked|needs_approval|failed`); `outcome` = domain verdict (`approved|changes_requested|informational`); `decision` = Mastermind's call on the ACK (`continue_local_changes|merge|revise|abort`). A review wanting edits is `status=done outcome=changes_requested` — **never** `status=CHANGES_REQUESTED`. The notification is a wake-up hint; the envelope on disk is the truth. Worker prose lives only in the envelope — the wire carries enumerated fields + a pointer, never arbitrary text.

**Every non-return message a worker sends upward (correction, intelligence, or mid-flight amendment) must begin with `[FROM <pane>]`**, for example `[FROM implementation:0.0] ⚠ Correction: …`; like every convention, it **must be baked into the job file to exist on the worker side**. A bare upward message reads as “a message from nobody” — on 2026-07-19, one bare correction from an implementation seat made the user think the message had crossed into the wrong window. The prefix makes the source self-evident and lets the commander attribute it to a pane.

**A cross-seat instruction that requires a receipt must embed the receipt command itself — conventions do not travel with a message; mechanisms do.** The `[FROM]` prefix and return channel are conventions of **this skill** and exist only in seats that loaded it. The other commander may never have loaded it, and `/clear` necessarily erases it (live 2026-07-21: one commander asked another fleet's commander to “reply with one-line confirmation”; the recipient wrote the reply as chat output in its own pane, so the channel never connected). Put the exact receipt command in the instruction: `Receipt method: tmux send-keys -t '<my-pane>' -l '[FROM <their-pane>] <one line>'`, then send `C-m` separately. If no receipt arrives, first capture the other pane; it probably answered locally.

## Fleet-loss recovery (server death, reboot, tmp cleanup)

Mailbox and job files live under tmp-class paths; the whole topology lives in one tmux server — a reboot, tmp cleaner, or tmux crash voids every contract's panes at once, and pane indices renumber even on routine kills. Drill: ① census survivors **per harness** — `tmux ls` AND `herdr workspace list`; a herdr fleet does not live in the tmux server and survives its death intact (2026-07-23: tmux socket+server gone, all herdr seats + mailbox unaffected; the durable envelope carried the in-flight return). Does the mailbox dir still exist?; ② relaunch seats (Stage 2 recipes); ③ re-register every open task from its job file — register is an upsert, job files are the surviving SoT (if tmp died too, re-author from the boards); ④ one line per open task: contract restored, re-run your return. After ANY pane kill/recreate or window relayout, re-register open contracts against the re-inventoried topology — a stored `reply_to` is a snapshot, not a live pointer.

## Remote workers over ssh

A worker on another machine (24/7 Windows box, cloud host) fits the same loop with two substitutions: its pane runs `ssh <host>`, and the watch surface becomes **handback + machine state read over ssh** — the files/configs it wrote and the actual effect (does the thing now work?), never its narration; its transcript lives in remote `~/.claude`, unreachable. Verify self-reported facts by reading the machine (2026-06-17: a claimed pubkey was `cat`-read on the box and fingerprint-matched before prod authorization). A remote worker blocked on an authority it lacks (prod key, secret) stops and hands back — the commander often holds that authority: execute the gated step yourself after explicit user approval, least-privilege. Its memory is the remote machine's, useless to the main line — harvest into the canonical skillbook yourself.

## Guardrails (the three true hard rules — everything above is a positive recipe)

1. **Harness-correct, serial delivery** (§2): one unique named buffer per Claude Code job — the unnamed global buffer races across panes; Pi gets one literal-line pointer, never the multiline body; deliver to panes serially.
2. **Dedupe before any outward retry** (§5): a possibly half-succeeded action (publish / deploy / post) is verified against present external state — a unique-key search plus a known-positive control — before a second attempt; a redirect or a queued message is never proof it landed.
3. **agent-view is not the chat editor, and the daemon is shared.** The agent-view input box has different key semantics (**enter = return, space = reply, ctrl+x = delete**): each blind Enter can hatch a *new* background daemon session while the UI looks unsubmitted (once mis-hatched 3 ghost sessions; one opened a duplicate PR). So: before appending a message to a worker, **confirm the pane is in chat view**; for a parallel session, spin your own `tmux new -d -s <concern>` rather than poking agent-view; **after any agent-view interaction, census what actually spawned**. Ghosts live in the shared claude daemon — a dead TUI does not kill them; **point-kill** by the pid whose `--session-id` / `--resume <jsonl>` matches, never the daemon tree (that orphans live workers' legitimate sub-agents). This daemon/session distinction is structural, not cosmetic.
